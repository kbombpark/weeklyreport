# 주간 보고 발행

Cofoundary가 클라이언트(대표/담당자)에게 매주 제출하는 보고 페이지를 발행한다.
담당자 입력은 두 경로 중 하나로 들어온다. 어느 쪽이든 리포트 데이터로 모인다.

```
Base "주간 보고 입력"  →  sync-base  ┐
                                       ├→ reports/<날짜>.yml → build → docs/ → Pages
라크 위키 회차 문서    →  sync-lark  ┘      (다듬는 지점)                     ↓
                                                            Base "주간 보고 링크" 갱신
```

어느 경로인지 모르면 **Base 를 먼저 확인한다** (`sync-base <slug> --list`).
비어 있으면 위키 문서 쪽이다.

클라이언트 슬러그: `1stcrm` `byteworks` `dmax` `jiranjigyo`.
각 `clients/<slug>/client.yml` 의 `lark.parentNode` 가 위키 폴더, `lark.project` 가
Base 레코드 키다.

## 절차

1. **회차 확정.** 날짜가 불명확하면 `node src/sync-base.mjs <slug> --list` 또는
   `node src/sync-lark.mjs <slug> --list` 로 입력된 회차를 본다.
2. **변환.**
   - Base 입력: `node src/sync-base.mjs <slug> <YYYY-MM-DD>`
   - 위키 문서: `node src/sync-lark.mjs <slug> <YYYY-MM-DD>` (못 찾으면 `--doc <노드토큰>`)

   변환 요약에 `요약 없음` 이 뜨면 그대로 발행하지 말고 사용자에게 알린다.
   `발행 제외 필드: 내부 메모 ...` 는 정상이다 — 그 내용은 데이터로 넘어오지 않으며,
   궁금해도 Base 에서 따로 읽어 보고서에 싣지 않는다.
3. **직전 회차와 대조.** `clients/<slug>/reports/` 의 이전 파일을 읽는다.
   이 대조가 이 스킬의 핵심이다 — 건너뛰면 그냥 변환기와 다를 게 없다.
4. **대외 보고로 다듬는다.** 아래 편집 규칙.
5. **빌드·확인.** `npm run build` 후 `docs/<slug>/<날짜>.html` 을 실제로 열어 본다.
6. **커밋·푸시는 사용자 승인 후.** 푸시하면 클라이언트가 보는 페이지가 바뀐다.
7. **Base 갱신.** `node src/update-base.mjs <slug> <날짜>` 로 미리보기 → 승인 후 `--write`.

## 이 스킬의 존재 이유

변환기(`sync-base` / `sync-lark` / 웹 입력 페이지)는 담당자가 쓴 문장을 **구조에만
맞춰 배치**한다. 그 결과물은 보고서가 아니라 초안이다. 그대로 내보내면 대표에게
작업 목록이 배달된다.

**이 스킬이 하는 일은 그 초안을 대표의 언어로 다시 쓰는 것이다.** 사실을 바꾸지
않으면서, 읽는 사람이 대표라는 전제로 문장을 다시 세운다. 이 단계를 건너뛸 거면
스킬을 쓸 이유가 없다.

읽는 사람은 이 프로젝트에 돈을 대는 사람이고, 보고서에 5분을 쓴다. 그 사람이
알고 싶은 것은 세 가지뿐이다.

1. 일정대로 가고 있나
2. 내가 지금 결정해줘야 할 게 있나
3. 돈이나 기간이 바뀌나

## 대표의 언어로 바꾸는 법

### 1. 작업이 아니라 판단을 먼저 쓴다

요약의 첫 문장은 진척에 대한 판단이어야 한다. 한 일의 나열로 시작하지 않는다.

> 초안: 코드 마이그레이션 QA 항목을 적용하고 DUR 코드를 이전했으며 신규 병원
> 생성 기능을 구현했습니다.
>
> 발행: 마이그레이션은 예정대로 진행 중이며, 이번 주 DUR 코드 이전까지
> 마쳐 남은 개발 범위는 DB 이전과 웹 전환 두 건입니다.

### 2. "검토했습니다"로 끝나는 항목에는 결론을 붙인다

검토·분석·파악·정리로 끝나는 문장은 대표에게 아무것도 알려주지 않는다.
무엇이 정해졌는지, 그래서 다음이 무엇인지 한 마디를 붙인다.
원본에 결론이 없으면 지어내지 말고 **사용자에게 묻는다.**

> 초안: 현행 구조와 개편안 간 격차 분석
>
> 발행: 현행 구조와 개편안의 격차를 분석해, 고객사–워크스페이스 관계를 새로
> 정의해야 한다는 결론을 얻었습니다. 설계 확정 후 개발에 착수합니다.

### 3. 기술 작업에는 사업적 결과를 붙인다

용어를 지우라는 게 아니다. 그 작업이 **무엇을 막았거나 가능하게 했는지**를 붙인다.

> 초안: 상용 서비스 아웃바운드 IP 고정
>
> 발행: 외부 연동 기관의 IP 제한에 대응해 상용 서비스 IP를 고정했습니다.
> 연동 차단 위험이 해소됐고, 이후 서버 증설에도 재작업이 없습니다.

### 4. 나열을 묶는다

같은 성격의 항목 다섯 개는 대표에게 다섯 개의 정보가 아니라 하나의 정보다.
묶고, 숫자로 말한다.

> 초안: 대응 13건 — 9건 완료 / 3건 백로그화 / 1건 진행 중
>
> 발행: 운영 이슈 13건 중 9건을 처리했고, 3건은 다음 스프린트로,
> 1건은 이번 주 마무리됩니다. (숫자가 이미 판단을 담고 있으면 그대로 둔다)

### 5. 결정 요청을 맨 앞으로 끌어올린다

대표가 해야 할 일이 보고서 맨 아래 요청사항에만 있으면 늦는다. 결정이
일정에 영향을 주면 요약에도 한 문장으로 올린다.

> 발행: …이번 주는 DB 이전을 진행합니다. **DB 이전 작업 가능 시간대를
> 확정해주셔야 다음 주 일정이 유지됩니다.**

### 6. 완곡어법을 쓰지 않는다

"~하는 부분에 대한 검토가 필요할 것으로 보입니다" 같은 문장은 아무 말도 하지
않는다. 필요하면 필요하다고, 늦으면 늦는다고 쓴다. 지연은 사유 한 줄과
새 목표일을 붙여 그대로 적는다.

### 7. 하지 않는 것

- **사실을 바꾸지 않는다.** 원본에 없는 수치·날짜·완료 판정을 만들지 않는다.
  빠진 정보는 채우지 말고 사용자에게 목록으로 되묻는다.
- **미완료를 완료로 올리지 않는다.** 근거 없이 상태를 승격하지 않는다.
- **과장하지 않는다.** "성공적으로", "완벽히" 같은 수식은 신뢰를 깎는다.

## 정확성 규칙 (문체와 무관하게 항상)

- **이월 대조.** 직전 회차 "이번 주 계획"의 각 항목이 이번에 완료·미완료 중
  무엇인지 확인한다. 원본에 언급이 없으면 지어내지 말고 사용자에게 되묻는다.
- **미완료는 남긴다.** 사유 한 줄 + 새 목표일을 붙여 `진행중` 으로.
- **클라이언트가 할 일은 전부 `요청사항`으로.** 본문에 묻어두지 않는다.
  직전 회차 요청사항에 회신이 없으면 재요청으로 다시 올린다.
- **일정·비용 변동은 `이슈 항목`에 숫자로.** 금액, 날짜, 기간.
- **리스크에는 태그를 붙인다.** `확인 필요` `일정 미확정` `비용` `논의 필요` 등.
- **내부 표현을 지운다.** 저장소명·브랜치·티켓 번호·내부 코드네임·담당자 실명·
  추측·변명. 내부 메모 필드의 내용은 어떤 경우에도 싣지 않는다.
- **표 안의 항목은 명사형 종결.** 요약·리스크·요청사항은 "~했습니다 /
  ~합니다 / ~요청드립니다" 체.

## 변환 후 자가 점검

발행 전에 다음을 확인한다. 하나라도 걸리면 다시 쓴다.

1. 요약 첫 문장이 **판단**인가, 작업 나열인가
2. "검토/분석/파악"으로 끝나고 결론이 없는 항목이 남아 있나
3. 대표가 이번 주에 해야 할 결정이 요약과 요청사항 **둘 다**에 있나
4. 지난 회차 계획 중 언급되지 않고 사라진 항목이 있나
5. 일정이나 비용이 바뀌었는데 숫자 없이 서술만 있나
6. 담당자가 쓴 문장이 **그대로** 남아 있는 곳이 있나 — 있다면 그 항목은
   아직 변환되지 않은 것이다

## 데이터 스키마

```yaml
period: 2026.09.21 – 09.27
asOf: 2026.09.21
source: <위키 노드 토큰>        # sync 가 남긴다. Base 갱신에 쓰인다.
stats:                          # 상단 3칸 (선택)
  - { label: 보고 기간, value: 09.21–09.27, mono: true }
  - { label: 핵심 마일스톤, value: ... }
  - { label: 전체 상태, pill: { text: 정상 진행, tone: good } }
summary: 3~4문장
sections:
  - type: table                 # 영역/내용/상태 표. status 없으면 2열
    title: 지난주 완료 산출물
    rows:
      - area: 개발
        status: { text: 완료, tone: good }    # tone: good | prog
        items: [항목, { text: 항목, sub: [하위] }]
  - type: notes                 # 태그 + 한 줄
    title: 리스크 및 의존성
    items: [{ tag: 확인 필요, text: ... }]
  - type: card                  # 강조 카드
    title: 요청사항
    items: [{ text: ..., sub: [...] }]
  - type: dual                  # 좌우 2단
    title: Safe Intelligence
    columns:
      - { label: 지난주 한 일, items: [...] }
      - { label: 이번주 할 일, items: [...] }
  - type: text                  # 자유 문단
    title: 향후 방향
    text: [문단, 문단]
```

본문에서 `**굵게**` 만 지원한다.

## 하지 말 것

- `docs/` 직접 수정. 빌드 산출물이며 매 빌드마다 지워진다.
- `clients/*/legacy/` 의 기존 HTML 수정. 이미 클라이언트에게 전달된 링크다.
- 라크 원본 문서 수정. 담당자의 작업물이다. 보고 내용에 문제가 있으면
  문서를 고치지 말고 사용자에게 알린다.
- 승인 없는 push, 승인 없는 `update-base --write`.
